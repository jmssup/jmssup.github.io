x86-64 아키택쳐의 stack 구조와 비교하여 aarch64 아미택쳐에서의 stack 구조를 이해하기 위한 글을 작성하고자 한다.

+ ROP, JOP를 어떻게 진행하는지도 알아보고자 한다. ROP, JOP 관련 내용은 _Pwnable 카테고리의 글로 작성할 예정이다.

 

aarch64의 stack 구조

일단 aarch64 아키텍쳐 특징은 아키택쳐 차원에서 어셈블리 명령어 자체가 32비트 즉, 4바이트로 통일되어 있다.

이러한 특징은 스택 구성에도 영향을 준다.

 

x86-64에서 이전 스텍프레임 주소 정보와 return address 정보를 저장하는 공간을 만들고 사용하듯이 aarch64도 동일하게 스택에 저장을 하고 재사용을 한다. 또한 프로그램 동작과정에 있어서 필요한 정보들을 레지스터에 담아 사용하는 방식은 두 아키텍쳐 모두 비슷하기에 관련해서 서로 어떻게 부르며 비슷한 역할을 하는 레지스터들을 칭하는지 적어보겠다.

 

aarch64는 x86-64와 비슷하게 stack 구조를 만들고 동작하는 것 같으나 세부적으로는 동작과정과 스택프레임 구성을 위한 단계가 다르다. 이는 글을 작성하며 풀어나가 보겠다.

 

sp: x86-64의 rsp로 현재 스택의 최하단 주소를 저장한다.

x29: x86-64의 rbp로 현재 스택프레임의 base 주소를 저장한다.

x30: return address를 저장한다.

 

aarch64는 x86-64와 다르게 return address를 x30 레지스터에 저장하고 이를 이용하여 pc 를 조정한다.

이는 leaf 함수에서 stack 구조가 달라지게 만든다. x86-64에서는 무조건 stack에 저장을 하는 구조로 이뤄지고 명령어도 stack 정보를 참조하도록 되어있어 무조건 stack에 return address 정보가 저장된다. 하지만 aarch64는 return address를 x30 레지스터를 참조하기에 leaf 함수에서는 x30 레지스터값을 참조하는 명령어만 존재하게 된다. 즉, aarch64의 leaf 함수에서는 return address를 저장하지 않는다.

 

또한 non-leaf 함수일 때의 이전 스택프레임으로 복귀하는 과정에서의 스택프레임 처리 과정도 다르다.

x86-64의 경우 스택의 SFP와 return address 정보를 이용하여 rbp와 rip를 복구하는 과정을 가지지만 aarch64의 경우 x30 레지스터를 이용하여 pc를 조정하기에 먼저 x29와 x30을 스택에 저장된 정보를 이용하여 복구하고 이후에 각 레지스터를 참조하여 조정한다.

 

또한 추가적으로 aarch64는 sp가 x86-64의 rsp 와 다르게 push, pop, call 같은 명령어를 통해 내부적인 계산이 이뤄지는 구조와 반대로 해당 push, pop, call 같은 명령어가 없기에 수동적인 계산이 요구되어 명령어에 직접적으로 계산식이 드러난다. 

 

이와 함께 aarch64는 하드웨어적으로 memory align이 강제된다.

모든 명령어는 4byte로 통일되어 있기에 각 명령어들의 주소는 4byte단위로 정렬되어있다. 또한 sp 레지스터의 경우 저장된 값에 대하여 16바이트 정렬이 강제로 요구되는데 이는 stp / ldp (Store,Load) 명령어들로 sp에 저장된 주소 위치(stack)에서 16바이트만큼 읽어와서 두 개의 레지스터에 저장, 혹은 반대 방향으로의 과정이 빈번하게 일어나기에 효율을 위해 sp에 대하여 16바이트 정렬을 강제한다.

 

그래서 위와 같은 특징들로 인하여 aarch64의 경우 x86-64와 세부적으로는 stack에 대하여 처리 과정이 다르며, 저장된 값들에도 패딩용 값이 들어가기 쉽다.
