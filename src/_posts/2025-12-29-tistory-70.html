클라이언트와 서버 사이에서 데이터가 전송될 때의 중간 관리자

① 포워드 프록시 (Forward Proxy)

보통 우리가 "프록시 서버"라고 부를 때 의미하는 방식입니다. 클라이언트(사용자) 측에 위치합니다.

  • 역할: 클라이언트를 대신해 인터넷에 연결합니다.
  • 장점:
    • 익명성: 서버는 실제 클라이언트가 누구인지 알 수 없고 프록시 서버의 IP만 보게 됩니다.
    • 우회: 특정 국가에서 차단된 사이트에 접속할 때 유용합니다.
    • 제한: 회사 내부망에서 특정 유해 사이트 접속을 차단하는 용도로도 쓰입니다.

② 리버스 프록시 (Reverse Proxy)

Nginx의 핵심 역할입니다. 서버(웹 서비스) 측 앞에 위치합니다.

  • 역할: 클라이언트의 요청을 받아 내부 서버(Node.js, Java 등)로 배분합니다.
  • 장점:
    • 보안: 실제 서버의 IP를 외부에 노출하지 않아 공격으로부터 보호합니다.
    • 로드 밸런싱: 여러 대의 서버에 요청을 골고루 나눠주어 과부하를 막습니다.
    • 캐싱: 자주 찾는 데이터를 미리 저장해두었다가 서버까지 가지 않고 바로 응답해 속도를 높입니다.

 

주요 보안 이점 4가지

1. 서버 은닉 (IP 및 인프라 보호)

가장 큰 이유는 실제 서버의 정체(IP 주소)를 숨기는 것입니다.

  • 직접 연결: 해커가 서버의 공인 IP를 알게 되면, 해당 서버의 취약점을 직접 공격(DDoS, 포트 스캔 등)할 수 있습니다.
  • 프록시 연결: 외부 사용자는 프록시 서버의 IP만 알 수 있습니다. 실제 데이터를 처리하는 백엔드 서버는 내부망(Private Network)에 숨겨두고 프록시만 외부에 노출함으로써 1차 방어선 역할을 합니다.

2. SSL/TLS 종단점 (Encryption Termination)

암호화 통신인 HTTPS를 처리하는 일은 서버에 상당한 자원을 소모하게 합니다.

  • 프록시 서버에서 SSL 인증서를 관리하고 암호화/복호화 과정을 전담하게 함으로써, 내부 서버는 비즈니스 로직에만 집중하게 합니다.
  • 보안 패치나 인증서 갱신을 프록시 서버 한 곳에서만 관리하면 되므로 보안 관리가 중앙 집중화되어 누락될 위험이 줄어듭니다.

3. 웹 애플리케이션 방화벽(WAF) 역할

프록시는 서버로 들어오는 모든 요청을 먼저 검사할 수 있는 위치에 있습니다.

  • 필터링: 비정상적인 요청(예: SQL Injection, Cross-Site Scripting(XSS) 패턴)이 감지되면 실제 서버에 도달하기 전에 차단합니다.
  • 요청 제한: 특정 IP에서 너무 많은 요청이 들어오면 이를 차단하거나 지연시켜 DDoS 공격의 피해를 최소화합니다.

4. 세밀한 접근 제어 (ACL)

프록시 설정에서 특정 국가의 IP를 차단하거나, 허가된 관리자 IP만 특정 페이지(/admin)에 접속할 수 있도록 제어할 수 있습니다. 서비스 코드 자체를 수정하지 않고도 설정 파일 하나로 강력한 접근 제어를 구현할 수 있다는 장점이 있습니다.

 

 

 

성능적 이점 3가지

1. 부하 분산 (Load Balancing)

사용자가 갑자기 몰릴 때, 한 대의 서버가 모든 요청을 처리하면 서버가 터질 수 있습니다. 프록시는 여러 대의 서버를 뒤에 세워두고 요청을 골고루 나누어 줍니다.

  • 가용성: 서버 한 대가 고장 나더라도 프록시가 이를 감지하고 정상적인 다른 서버로 요청을 보내 서비스가 중단되지 않게 합니다.
  • 확장성: 트래픽이 늘어나면 서버를 새로 추가하고 프록시 설정에 등록만 하면 됩니다.

2. 응답 속도 향상 (Caching & Compression)

프록시는 클라이언트와 서버 사이에서 "더 빠르게" 데이터를 전달하는 최적화 작업을 수행합니다.

  • 캐싱(Caching): 서버가 한 번 만든 결과물을 프록시가 저장해 둡니다. 다음 사용자가 같은 것을 요청하면 서버까지 가지 않고 프록시가 즉시 답변합니다. (서버 부하 감소 + 사용자 대기 시간 단축)
  • 콘텐츠 압축: 데이터를 보내기 전 프록시 단계에서 Gzip 등으로 압축하여 전송량을 줄입니다. 모바일 환경처럼 네트워크가 느린 곳에서 효과가 큽니다.

3. 구조적 유연성 (Service Abstraction)

사용자에게는 하나의 도메인(example.com)만 보여주지만, 뒤에서는 여러 기술 스택을 섞어 쓸 수 있습니다.

  • URL 라우팅: * example.com/api → Node.js 서버로 전달
    • example.com/blog → WordPress(PHP) 서버로 전달
    • example.com/static → Nginx가 직접 이미지 파일 서빙
  • 무중단 배포: 새로운 버전의 서버를 띄운 뒤, 프록시 설정만 살짝 바꿔서 새 서버로 연결하면 사용자는 서비스 중단을 전혀 느끼지 못합니다.
